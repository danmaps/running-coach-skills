# Post-Run Debrief

Compare the run that happened to the run that was planned, and keep the useful signal for the plan.

## Process

1. Find the prescribed session: the plan document, or the workout the agent sized for that day in conversation.
2. Read the completed activity from the user's data sources, in the README's priority order (platform health store first, then Strava via MCP on paid plans or GPX export, then other services or a manual log): distance, duration, pace, route, heart rate and splits if available. If no source has the activity recorded, ask the user for the basics (distance, time, how it felt) and work from that.
3. Compare plainly: distance vs target, effort vs prescribed effort (pace and heart rate as evidence, feel as the user's evidence), and anything notable in the splits (started fast and faded, strong finish, stopped early).
4. Ask for or use the user's own report: how the legs felt, anything that hurt, anything unusual. Subjective feel is data; record it.
5. Give a short takeaway: what this run means for the next session (repeat, progress, or back off), in one or two lines.
6. Save the debrief note where the weekly check-in will find it: a notes section in the plan document or a debrief log the user's setup defines.

## Output

- Planned vs actual, briefly.
- One observation from the data.
- The user's feel, in their terms.
- The implication for the next run.

## Guardrails

- One run is one data point. Never rewrite the plan off a single good or bad day; patterns come from the weekly check-in.
- Pain reported in a debrief gets a recommendation to see a professional if it persists, never a diagnosis.
- Keep the tone even: a short run is still reported accurately, without disappointment or hype.
